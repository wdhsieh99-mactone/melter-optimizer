# 80T 熔鋁爐升溫曲線最佳化系統

以真實產量與感測器資料校正過的物理模型，幫助操作員在滿足出湯時限的前提下，找出能最小化
燃氣與氧化燒損成本的升溫排程。附帶蓄熱式燃燒系統的燒嘴健康監測子模型。

## 這個系統做什麼

- **升溫排程最佳化**：輸入投料重量、合金種類、前爐殘湯量、出湯時限，搜尋能滿足時限、
  成本最低的頂溫設點／切換時機／過剩空氣率組合，並與傳統固定 1100°C 做法比較。
- **歷史回測**：把最佳化結果拿去對照真實歷史爐次的燃耗與燒損，驗證模型不是憑空瞎猜。
- **參數敏感度驗證**：系統化檢查每個模型參數（空燃比、燃料熱值、頂溫設點等）調整後，
  結果變化的方向跟幅度是否合乎物理與現場實務數字。
- **蓄熱系統健康監測**：從感測器資料建立蓄熱介質集總熱容模型，可比對即時資料與健康基準，
  偵測蓄熱箱是否有異常（阻塞、偏流、劣化）。

## 快速開始

### 1. 安裝相依套件

```bash
pip install -r requirements.txt
```

### 2. 準備資料檔案

程式需要以下真實資料檔案（**未納入版本控制**，屬公司機密生產資料/手冊版權內容，需自行放到
專案根目錄，路徑見 `src/data_loader.py`）：

| 檔案 | 用途 |
|---|---|
| `115年 MFX生產紀錄.xlsx` | 生產紀錄（爐號、合金、投料量、燃耗、時間戳） |
| `mfa_20260707-0714_wide.csv` | MFA 爐 5 秒間隔感測器資料（一週份） |
| `40522-Melting Furnace Manual.pdf` | Mechatherm 原廠操作手冊 |

若沒有這些檔案，`app.py` 的單爐模擬分頁仍可運作（使用已校正好的 `src/calibrated_constants.json`
與 `src/regenerator_baseline.json`），但「歷史回測」分頁跟重新校正指令會需要它們。

### 3. 啟動操作員儀表板

```bash
streamlit run app.py
```

瀏覽器會自動開啟，包含三個分頁：

- **🚀 即時單爐最佳化模擬**：輸入投料重量（公噸）、前爐殘湯（公噸）、合金種類、目標湯溫、
  出湯時限，取得建議的升溫排程與傳統做法的對比圖表（燃氣量、成本、燒損）。
- **📊 歷史爐次回測分析**：對真實歷史爐次跑最佳化，比較「若當初這樣操作」能省多少。
- **📖 手冊**：4 燒嘴 2 對蓄熱式燃燒系統的操作原理摘要。

頁面頂端會顯示模型是否已用真實資料校正過（綠色橫幅），以及校正品質數字。

## 常用指令

```bash
# 重新用真實生產資料校正物理模型常數（資料更新後才需要重跑）
python -m src.calibration

# 拿最佳化結果對照真實歷史爐次的燃耗/燒損
python -m src.evaluator

# 重新掃描每個參數的方向性與合理性，重新產生 SENSITIVITY_REPORT.md
python -m src.sensitivity_analysis

# 重新校正蓄熱介質熱容模型與健康基準值
python -m src.regenerator_model

# 執行測試（32 個測試，涵蓋物理模型、最佳化、敏感度、蓄熱子模型）
pytest tests/ -v
```

## 專案結構

```
melter2/
├── app.py                          # Streamlit 操作員儀表板
├── src/
│   ├── physics_model.py            # 熱力學/燃燒效率/氧化燒損物理模型
│   ├── optimizer.py                # 升溫排程搜尋與模擬
│   ├── data_loader.py              # 真實生產/感測器資料讀取與清理
│   ├── calibration.py              # 物理常數校正（對真實資料擬合）
│   ├── evaluator.py                # 對真實歷史爐次回測
│   ├── sensitivity_analysis.py     # 參數方向性/合理性驗證
│   ├── regenerator_model.py        # 蓄熱介質熱容子模型與健康指標
│   ├── calibrated_constants.json   # 已校正的物理常數（產出物）
│   └── regenerator_baseline.json   # 已校正的蓄熱健康基準（產出物）
├── tests/                          # pytest 測試
├── MELTER_KNOWLEDGE.md             # 從 Mechatherm 手冊整理的知識庫
├── PLAN.md                         # 開發歷程與核心 bug 修復紀錄
├── SENSITIVITY_REPORT.md           # 自動產生：參數敏感度驗證報告
├── CASE_STUDY.md                   # 傳統 vs. 最佳化排程的具體案例比較
└── REGENERATIVE_SYSTEM_ANALYSIS.md # 因子影響排名與蓄熱系統分析
```

## 延伸閱讀

想了解模型是怎麼來的、踩過什麼坑、目前還有哪些已知限制，依序看這幾份文件最有效率：

1. **`MELTER_KNOWLEDGE.md`** — 這台 80T 靜置式熔鋁爐（Mechatherm 製造，4 燒嘴 2 對蓄熱式
   燃燒系統）的硬體規格與控制邏輯，從原廠手冊整理而來。
2. **`PLAN.md`** — 為什麼要做這個系統、校正過程中發現原本工具有什麼問題（例如「最佳化」
   方案其實比實際操作更耗氣的核心 bug）、怎麼修的。
3. **`SENSITIVITY_REPORT.md`** — 每個參數調整後，結果變化方向是否合乎物理直覺、數值是否
   落在合理範圍，包含過程中發現並修復的三個真正的程式碼 bug。
4. **`CASE_STUDY.md`** — 一個具體案例：65 噸、6 小時、5083 合金，傳統排程 vs. 最佳化排程
   的完整數字對比。
5. **`REGENERATIVE_SYSTEM_ANALYSIS.md`** — 哪些因子對成本影響最大（結論：頂溫設點與爐床
   輻射面積 > 空燃比與燃料熱值）、蓄熱式燃燒系統在模型內怎麼實踐、蓄熱介質健康監測子模型
   的設計與驗證過程。

## 已知限制

- 校正資料僅涵蓋 MFA 爐一週的感測器資料，MFB/MFC 爐沒有對應的感測器 CSV。
- 「傳統模式」比較基準是程式內建的代表性情境（固定 1100°C／25% 過剩空氣），並非逐爐重播
  的真實歷史操作紀錄（現場沒有留存每爐真實頂溫設點）。
- 蓄熱介質健康監測子模型尚未接回主要成本模型，是獨立旁路工具；`tt111-114` 感測器欄位的
  物理意義是根據訊號行為強力推論所得，尚未經現場工程正式確認。

完整清單見 `PLAN.md` 與 `REGENERATIVE_SYSTEM_ANALYSIS.md` 的「尚未做的部分」段落。
